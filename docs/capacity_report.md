# 容量与成本：数据量小，不等于不知道量大了会怎样

一句话结论：**10 万条以内，向量检索用不着任何数据库**。这个判断不是猜的，是量出来的；
顺带发现并修掉了一个真的会线性爆炸的瓶颈（逐条 Python 算余弦）。

---

## 一、为什么要做这件事

面试官问「10 万条文档怎么办」，答「我只有 119 条」直接掉分。

但造 10 万条假健身内容去凑数，是更糟的选择：

- 一问来源就崩（「这些内容哪来的」）；
- 假语料会把检索质量带下去，指标反而更难看；
- 面试官关心的是**你的判断力**，不是你的数据量。

所以这里只测工程指标：**延迟、内存、召回**。这三样只跟「条数 × 维度 × 实现方式」有关，
跟自己写的文本是不是真实内容无关。做法是拿真实的 119 条 bge-m3 向量（1024 维）当基底，
随机采样 + 加 0.02 的高斯噪声扩到目标规模，重新归一化 —— 向量分布与真实同源，
测出来的数是有意义的。

脚本：`bench_scale.py`　结果：`bench_scale.json`

## 二、规模实验：同一份代码，四种规模

机器：Intel64 / Python 3.14 / numpy 2.5.5　top_k=12（对应线上 `RECALL_K`）

| 条数 | 向量内存(float32) | A 逐条 Python | B 矩阵全排序 | C 矩阵 + top-k | 加速 |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 119 | 0.5 MB | 57.3 ms | 0.1 ms | 0.1 ms | ~600× |
| 1 000 | 3.9 MB | 445.1 ms | 0.6 ms | 0.5 ms | ~800× |
| 10 000 | 39.1 MB | 4.02 s | 6.1 ms | 5.7 ms | ~710× |
| 100 000 | 390.6 MB | **43.74 s** | 73.8 ms | 66.8 ms | ~655× |

三个能直接说的结论：

1. **瓶颈不在「有没有向量库」，在「怎么算余弦」**。10 万条时纯 Python 一次查询 43.7 秒，
   换成矩阵乘是 66.8 毫秒 —— 差 655 倍。这个差距不会因为上了 pgvector 而自动消失，
   因为锅不在存储层。
2. **Python 的 float 对象比 float32 数组占 8 倍内存**。1 万条时：矩阵 39 MB，
   而 `list[list[float]]` 要 313 MB。所以「先转成矩阵」不只是快，还是省内存。
3. **10 万条暴力检索完全够用**。1024 维 × 10 万条 = 390 MB 常驻内存，
   一次全量点积 67 ms。而一次真实提问端到端 3.4 秒（见第四节），
   67 ms 占 2%。为这 2% 去运维一套向量数据库，是过度设计。

### 什么时候才真的需要 ANN / pgvector

按上表线性外推（点积耗时与条数成正比）：

| 条数 | 内存 | 单次暴力检索 | 判断 |
| ---: | ---: | ---: | --- |
| 10 万 | 390 MB | 67 ms | 够用，不用换 |
| 100 万 | 3.9 GB | ~670 ms | **该换了**，P95 会被拖垮 |
| 1000 万 | 39 GB | ~6.7 s | 必须换，且要分片 |

所以阈值在 **十几万到一百万之间**，取决于机器内存和 P95 要求。
真要上，优先 pgvector（跟业务库同一个，少一套运维），其次 hnswlib（最快，但要自己管索引文件）。
代价是召回率损失（HNSW 典型 95~99%），要重新跑一遍四桶分解确认 `miss` 不涨。

## 三、顺手做的改造：逐条算余弦 → 矩阵乘

原来 `main.py` 是手写的：

```python
def cosine(a, b):
    dot = sum(x * y for x, y in zip(a, b))
    ...
for d, kb_vec in zip(KB, get_kb_vectors()):
    ranking.append({... "score": round(cosine(q_vec, kb_vec), 4)})
```

119 条时是 57 ms，被后面 LLM 的 3 秒盖住，所以「看起来没问题」——
但它也是唯一一个**会随数据量线性爆炸**的环节。

改成两件事：

1. 全库向量预归一化成矩阵（`kb_matrix()`，只建一次）：归一化后 **点积 == 余弦**；
2. 一次 `矩阵 @ 查询向量` 拿到全库分数（`all_vec_scores()`）。

四处同构的循环（`search_kb_vector` / `rank_one` / `hybrid_rank` / `search_kb_rewrite`）
全部收口到这两个函数，避免「改了一处忘了另一处」——这个项目因为两份逻辑看起来一样，
已经吃过一次亏（`eval.py` 覆盖写）。

numpy 是可选的：没装就自动退回逐条 `cosine`，功能不变，只是慢。所以部署环境不会因此挂掉。

### 改完必须证明没改坏

矩阵化最容易出的错是「快但算错」，所以做了三层核对：

- 数值：`all_vec_scores` 与逐条 `cosine` 的最大绝对误差 **1.0e-6**（float32 精度）
- 排序：1 万条规模下，A（逐条）与 C（矩阵）的 top-12 **分数多重集一致、id 集合一致**
- 回归：200 集评测 `hit@1 93.3% / hit@2 95.2% / 整体 85.0%`，与改造前逐位一致；
  5 个测试文件（204 项）全过

顺带解释一个容易被误判成 bug 的现象：某次核对显示 top-12「集合不一致」，
查下去是原实现**先把分数 round 到 4 位再排序**，分数并列时按原序；
新实现用原始分数排序，并列处会换人。同样的分数、同样的集合，只是顺序不同 ——
这不是错，但如果不查清楚，很容易把「并列」当成「改造引入的 bug」去修。

## 四、成本：钱花在哪

脚本：`cost_report.py`（每条都清查询缓存，真走一遍模型）　明细：`cost_report.json`

12 条真实问法（取自公众号后台日志，不是对着正文反推的题）：

| 项目 | 每条平均 |
| --- | ---: |
| 端到端耗时 | 3375 ms（P95 5099 ms） |
| embed 调用 | 1 次 / 10 token |
| rerank 调用 | 1 次 / **2097 token** |
| 生成输入 | 251 token |
| 生成输出 | 174 token（其中思维链 126） |

### 最反直觉的一条：rerank 占 83% 的 token

```
rerank   2097  ████████████████████████████████████████  83%
输入      251  █████                                    10%
输出      174  ███                                       7%
embed      10  ▏                                         0%
```

原因很简单：精排要把 12 段候选（每段 100~200 字，约 170 token）连问题一起喂进去。
**召回条数直接乘在账单上**，而生成只吃 3 段。

所以「省钱」和「提速」指向同一个动作：**少召回几条**。
但这是有代价的 —— `RECALL_K` 从 12 降下来，得先确认 `miss`（真的没召回）不涨。

### 时间分布

一次请求的两段耗时（`timings`）：`retrieve_ms ≈ 3575`（embed + rerank）、`llm_ms ≈ 6729`。
retrieve 里 embed 只占几十毫秒，**rerank 吃掉了几乎全部**。

也就是说：4B 的精排模型，比向量检索慢 1000 倍、贵 8 倍，而它是这个项目命中率的来源
（换成 bge-reranker 时 20 条最难的问法从 14/20 掉到 8/20）。这是个明账上的取舍，不是疏漏。

### 三个杠杆，各自代价

| 杠杆 | 省什么 | 代价 | 现状 |
| --- | --- | --- | --- |
| 砍 `RECALL_K` 12→8 | rerank token −33% | `hit@ctx` 可能掉 | 没动，要先跑四桶 |
| 缩短 chunk 文本 | rerank token 同比例降 | 答案细节变少 | 没动，内容本来就薄 |
| 命中缓存 | **全部归零** | 只能覆盖重复问题 | 已有，LRU 500 条 |

缓存这一条值得单独说：命中时**一次模型都不调**，成本是 0。
所以「单次成本」这个数只能当上限看，真实账单取决于重复率 —— 而健身问题重复率天然很高
（「一周练几次」「蛋白吃多少」会反复被问）。

### 换算成月账单

单价不写死在代码里（会变，不同账号还有折扣）。填 `prices.example.json` 后重跑即可出钱：

```bash
cp prices.example.json prices.json   # 改成你控制台看到的价格
uv run python cost_report.py -n 12 --prices prices.json
```

按示例单价算的算例（**仅演示公式，不是真实报价**）：

| 规模 | 全部未命中缓存（上限） | 命中率 50% |
| --- | ---: | ---: |
| DAU 10 | 见脚本输出 | 减半 |
| DAU 100 | 见脚本输出 | 减半 |
| DAU 1000 | 见脚本输出 | 减半 |

公式：

```
单次成本 = embed_token/1e6 × 单价 + rerank_token/1e6 × 单价
         + prompt_token/1e6 × 单价 + completion_token/1e6 × 单价
月成本   = 单次成本 × DAU × 人均日提问次数 × 30 × (1 − 缓存命中率)
```

## 五、生成层：思维链吃掉一半成本，但不能一刀切关掉

输出单价通常是输入的 4 倍，而实测**输出里 75% 是思维链**。按上表的 token 量折算，
思维链约占总成本的一半 —— 一半的钱花在「想」上。

补全调用（`condense_llm`）早就关掉了推理，主生成一直没关。这次量了一把：
同一批 8 条问题、同一份资料、temperature=0，只差 `enable_thinking` 一个布尔。
脚本 `ab_thinking.py`，明细 `ab_thinking.json`。

| 指标 | A 默认（不传） | B 关推理 | 变化 |
| --- | ---: | ---: | ---: |
| 端到端耗时 | 5682 ms | 2138 ms | **−62.4%** |
| 输出 token | 279 | 40 | **−85.9%** |
| 答案字数 | 107 | 61 | −42.7% |
| **答案里的数字个数** | **4.6** | **2.2** | **−51.4%** |

看成本，关掉很划算。看质量，**数字少一半**是硬伤 —— 健身问答里克数、组数、次数就是价值本身，
答得短而空等于没答。两个具体例子：

- 「深蹲膝盖疼怎么办」：A 给出「关节刺痛或卡压感立刻停，肌肉酸胀可以继续；换腿举先稳定一两周再回原动作」；
  B 只说「换成腿举，不要硬撑」，**丢了那条安全边界**。
- 「推日之后二头还练吗」：B 反而保住了「仰卧臂屈伸补三头长头」这个细节 —— 所以不是「关了就一定差」。

**结论：保持默认开。** 这不是「哪个更好」的问题，是**要不要按问题类型分级**：
纯事实题（几斤、多少克、清单）不需要推理；涉及伤病、替代动作、禁忌的必须有。
做分级需要先能判断问题类型，那是下一件事，这轮没做。

顺带修掉一个体验问题：A 组原来的回答会说「**资料里**：一周掉 0.25 到 0.5 公斤」，
把内部概念漏给用户，而且不肯做斤/公斤换算。改提示词（「像跟学员说话，别提资料」）后变成
「一周掉 0.25 到 0.5 公斤，也就是半斤到一斤，算正常」—— 同样一份资料，答得像人话。

## 六、这套方法自己的边界（写在报告里，免得自欺）

1. **合成数据只验证工程指标，不验证检索质量**。加噪扩到 10 万条时，最近邻多半是同一个原型的副本，
   真实 10 万条语料的分布更散。所以这张表能回答「多快、多少内存」，不能回答「准不准」。
2. **只测了单机单进程**。多 worker 下每个进程各存一份矩阵，内存要乘 worker 数 ——
   这也是「什么时候该把向量挪到独立服务」的一个隐藏理由。
3. **没测并发**。表里是串行单次延迟，QPS 上限没测（GIL 下矩阵乘会释放锁，但 Python 层仍有开销）。
   要做压测得另起 locust/wrk，这轮没做。
4. **token 数是实测，单价是示例**。别把示例价当报价用。
